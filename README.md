## 1. Run it

```bash
git clone <repo-url>
cd team.random-
docker compose up --build
```

Open **http://localhost:8080** — no other steps needed.

> If port 8080 is busy, copy `.env.example` to `.env` and set `APP_PORT=8090` (or any free port).

## 2. How it's built

Four Docker containers, one published port:

| Service | Image / build | Listens | Published | Role |
|---|---|---|---|---|
| `nginx` | `nginx:1.27-alpine` | 80 | **:8080** (localhost only on the server) | Reverse proxy: `/register`, `/login`, `/logout` → auth; everything else → app; WebSocket upgrade on `/ws` |
| `auth` | `./auth` (node:22-alpine) | 3000 | no | Accounts (Postgres), bcrypt, signs RS256 JWTs; serves login/register/logout pages |
| `app` | `./app` (node:22-alpine) | 8000 | no | Home page, game pages, static files, WebSocket server, all game simulation (in memory) |
| `db` | `postgres:16-alpine` | 5432 | **no** | Stores the `users` table only; never reachable from outside |

**Named volumes:** `db_data` (Postgres data), `auth_keys` (RSA private key — mounted only in `auth`), `public_key` (RSA public key — written by auth, mounted read-only in app).

The game state lives entirely in memory in the `app` container. Restarting the app ends any running games; accounts and logins survive because they are stored in Postgres and in the signed cookie.

## 3. How the requirements are met

### Objective 1 — Infrastructure

- **Framework:** Express 4 (`app/src/server.js`, `auth/src/server.js`).
- **Compose:** `docker-compose.yml` at the repo root; `docker-compose.prod.yml` layered on top for the live server. GitHub Actions deploys `main` automatically via SSH.
- **nginx reverse proxy:** `nginx/nginx.conf` — routes auth paths to `:3000`, all other HTTP + WebSocket traffic to `:8000`; the only published port is 8080 (or `$APP_PORT`).
- **Postgres in its own container:** `db` service has no `ports:` key — it is unreachable from outside Docker. The `auth` container is the only service that connects to it.
- **Home page at `/`:** served by `app`; shows "Logged in as …" when a valid token cookie is present, or a login link otherwise.

### Objective 2 — Auth

- **Auth container behind nginx:** auth runs on port 3000, never published; nginx routes `/register`, `/login`, `/logout` to it.
- **bcrypt:** cost 12 (`bcryptjs`); passwords are never logged or returned; max 72 bytes enforced.
- **RS256 JWT with `exp`:** auth generates a 2048-bit RSA key pair on first start (stored on the `auth_keys` volume), signs tokens with the private key, and sets `exp` to 7 days. The `app` container verifies tokens with the public key (read-only volume mount) using `jsonwebtoken` with `algorithms: ["RS256"]` — it never calls auth or the database.
- **Keys on volumes:** logins survive container restarts because the key pair persists on the named volume.
- **HttpOnly SameSite=Strict cookie:** the `token` cookie is `HttpOnly; SameSite=Strict; Path=/`; gets `Secure` when `X-Forwarded-Proto: https`.
- **CSRF double-submit:** every state-changing form (register, login, logout) requires a CSRF token set as a cookie and echoed as a hidden form field; the server verifies both match.

### Objective 3 — Real-time shared space

- **Shared space:** the **lobby** — a round hall with a spinning carousel and ten team cells. Up to 40 players share it simultaneously.
- **Real-time movement / shoving / dragging:** the server simulates the lobby at 30 Hz; clients send held-key vectors (`{t:"in", x, y}`); the server resolves collisions, the carousel rotation, the Watcher AI, door animations, and broadcasts a full snapshot (`{t:"L"}`) every tick.
- **WSS through nginx:** the nginx config passes `Upgrade: websocket` through to the app server; on HTTPS the connection is `wss://`.
- **JWT checked in the handshake:** `app/src/server.js` reads the `token` cookie from the WebSocket upgrade request and verifies it before accepting the connection (403 on failure).
- **Username from the token only:** clients never send their username; the server uses `claims.sub` from the verified JWT for everything the connection does.

## 4. Objective 4 — Theory and Algorithms

### Procedural maze generation

Each team plays its own endless **shaft** generated by `app/shared/mazeworld.js` — a module shared by both the server (which runs the game) and the browser (which draws the walls). Because each floor is generated deterministically from `(match seed, team id, depth)` with a seeded PRNG ([mulberry32](https://gist.github.com/tommyettinger/46a874533244883189143505d203312c)), **the server only ever sends the seed** — never the walls — and both sides build identical shafts.

Floor generation pipeline (depth *d*, team size *n*):

1. **Perfect maze — randomised DFS (recursive backtracker):** a grid of `clamp(3+n, 4, 7)` columns × `min(8, 3+⌈d/2⌉)` rows is carved by a depth-first search with a seeded random stack. Every cell is reachable; there are no loops yet.
2. **Braiding:** a fraction `max(0.12, 0.6−0.06(d−1))` of dead-end walls are knocked through, adding loops so there is never a single forced path. Braiding shrinks with depth, making deeper floors feel more maze-like.
3. **Gate placement:** a doorway is cut in the bottom wall of the floor — the only way down. Its column is derived from the seed so a spectator can reconstruct any team's shaft starting at any depth.
4. **Station placement (BFS):** `max(1, min(n, 1+⌈d/2⌉))` stations (levers on odd floors, pressure plates on even) are placed by repeated BFS from the entry, the gate, and each previously placed station, always picking the most distant reachable cell. This forces the team to split up.
5. **Scaling:** light `window = max(1.6, 3.4−0.2(d−1)) + 0.25·max(0, stations−2)` seconds; more stations = more time but only just. Deeper floors: more stations, smaller braid fraction, faster Watcher.

### The Watcher's AI (A\* pathfinding)

The Watcher (the server-side monster) uses `k.navigate()` from `mazeworld.js`, which runs **A\*** over the cell graph (Manhattan heuristic, re-planned every 0.5 s) and steers the monster toward each waypoint with sub-cell precision. The Watcher has five modes:

| Mode | Behaviour |
|---|---|
| `sleep` | Dormant for the first 6 s on each floor (no Watcher on floor 1). |
| `patrol` | Wanders to random cells ≥ 300 px away. Speed scales with depth and team size. |
| `search` | Heads for the last heard noise (lever pull, plate fire, gate open — detected by BFS distance). |
| `hunt` | Locks onto the nearest visible player; uses A\* to navigate, direct steering within 230 px line-of-sight. Gives up after 6.5 s of chasing (enters `leave`). |
| `leave` | Retreats to a cell 5–9 BFS steps away for a cooldown, then returns to `patrol`. |

**Vision** is line-of-sight along a ray (walls block; open gates don't): `min(620, 380+30·max(0,depth−2))` px, so it sees further on deeper floors.

**Freeze mechanic:** touching a player freezes them; a teammate standing next to them for 2 s thaws them. If the whole team is frozen simultaneously: 5 s penalty, then everyone restarts at the top of the floor.

### Why the host can press **G** in the maze

The in-browser **G** key (how-to overlay) overlays the A\* path the server is using for the Watcher, the BFS distance field from the monster's current cell, the station ownership arrows, and the seeded cell graph — all reconstructed client-side from the same `mazeworld.js` the server uses, with no extra data from the server.

## 5. Testing

**Manual:** in the lobby, click **Add bots** to fill the session with server-controlled players, then press **Start**. Watch a full round play out.

**Automated end-to-end test** (requires a running stack on port 8080):

```bash
cd tests
npm install
node e2e.js
```

Should end with `all passed` (41 checks: security, bots, lobby, maze). Run it twice in a row; both must pass.
